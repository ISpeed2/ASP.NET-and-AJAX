# Оптимизация работы с базой данных и внешними HTTP API

## 1. Оптимизация запросов в Entity Framework Core

### Проблема N+1

Проблема N+1 возникает, когда приложение сначала выполняет один запрос для
получения основной коллекции, а затем делает отдельный запрос для каждого её
элемента.

Например, сначала загружаются все клиенты, после чего в цикле отдельно
запрашиваются заказы каждого клиента:

```csharp
var customers = await db.Customers.ToListAsync();

foreach (var customer in customers)
{
    var orders = await db.Orders
        .Where(order => order.CustomerId == customer.Id)
        .ToListAsync();
}
```

Если найдено 100 клиентов, приложение выполнит 101 запрос: один запрос клиентов
и ещё 100 запросов заказов. Количество обращений к базе данных растёт вместе с
числом записей, поэтому такой код плохо работает под нагрузкой.

Проблема может быть особенно незаметной при использовании Lazy Loading: запросы
выполняются автоматически в момент обращения к навигационному свойству.

### Проекция через `Select`

Если endpoint должен вернуть DTO, лучше сразу сформировать его внутри запроса:

```csharp
var result = await db.Customers
    .AsNoTracking()
    .Select(customer => new CustomerOrdersDto
    {
        Id = customer.Id,
        Name = customer.Name,
        OrdersCount = customer.Orders.Count(),
        TotalSum = customer.Orders
            .Sum(order => (decimal?)order.Total) ?? 0m
    })
    .ToListAsync();
```

EF Core преобразует выражение в SQL. База данных сама выполнит `COUNT` и `SUM`,
а приложению вернутся только необходимые столбцы. Это уменьшает число запросов,
объём передаваемых данных и расход памяти.

Приведение к `decimal?` и `?? 0m` позволяет корректно обработать клиента, у
которого ещё нет заказов.

### `AsNoTracking`

По умолчанию EF Core отслеживает загруженные сущности, чтобы затем сохранить их
изменения через `SaveChangesAsync`. Для операций только на чтение это не нужно.

```csharp
var products = await db.Products
    .AsNoTracking()
    .ToListAsync();
```

`AsNoTracking` уменьшает затраты памяти и процессорного времени. Его удобно
использовать в GET-запросах, отчётах и других read-only сценариях.

### `Include` и декартово произведение

`Include` загружает связанные сущности:

```csharp
var customers = await db.Customers
    .Include(customer => customer.Orders)
        .ThenInclude(order => order.Items)
    .AsNoTracking()
    .ToListAsync();
```

Такой подход подходит, если приложению действительно нужны полноценные
сущности и их связи. Однако один большой запрос с несколькими коллекциями может
создать множество повторяющихся строк в результате SQL JOIN. Это называют
декартовым взрывом.

В таком случае можно использовать разделённый запрос:

```csharp
var customers = await db.Customers
    .Include(customer => customer.Orders)
        .ThenInclude(order => order.Items)
    .AsSplitQuery()
    .AsNoTracking()
    .ToListAsync();
```

`AsSplitQuery` выполняет несколько SQL-запросов вместо одного большого JOIN.
Это может сократить объём повторяющихся данных, но увеличивает число обращений
к базе. Выбирать вариант следует после измерений на реальных данных.

### Сложные отчёты и сырой SQL

LINQ удобен для большинства запросов, но сложный отчёт иногда проще и понятнее
выразить через SQL. Например, оконная функция `RANK` позволяет пронумеровать
клиентов по сумме заказов:

```sql
SELECT c.Id,
       c.Name,
       SUM(o.Total) AS Total,
       RANK() OVER (ORDER BY SUM(o.Total) DESC) AS Rank
FROM Customers AS c
JOIN Orders AS o ON o.CustomerId = c.Id
WHERE o.CreatedAt >= @since
GROUP BY c.Id, c.Name
ORDER BY Total DESC
OFFSET 0 ROWS FETCH NEXT 5 ROWS ONLY;
```

Параметры нельзя добавлять в SQL конкатенацией строк. Параметризованный запрос
защищает от SQL injection и позволяет базе данных переиспользовать план
выполнения.

В EF Core 8 результат, не являющийся сущностью, можно получить через
`SqlQuery<T>`. Для полного контроля над SQL также часто используют Dapper.
Dapper не выполняет change tracking, поэтому хорошо подходит для отчётов и
простых read-only запросов, но разработчик сам отвечает за написание SQL.

### Измерение производительности

Оптимизацию следует подтверждать измерениями. Для простой проверки времени
можно использовать `Stopwatch`:

```csharp
var stopwatch = Stopwatch.StartNew();

var result = await service.GetOrdersAsync(cancellationToken);

stopwatch.Stop();
logger.LogInformation("Запрос выполнен за {ElapsedMs} мс",
    stopwatch.ElapsedMilliseconds);
```

Кроме времени выполнения полезно сравнивать количество SQL-запросов, объём
полученных данных, потребление памяти и поведение под параллельной нагрузкой.

## 2. `IHttpClientFactory`

### Зачем нужна фабрика клиентов

Создавать новый `HttpClient` для каждого запроса не рекомендуется. Каждый
экземпляр со своим обработчиком может открывать новые сетевые соединения, а их
частое создание и закрытие под нагрузкой способно привести к исчерпанию сокетов.

Один статический клиент решает часть проблемы, но может слишком долго хранить
старые DNS-данные. `IHttpClientFactory` централизованно создаёт клиенты и
управляет временем жизни внутренних обработчиков соединений.

### Типизированный клиент

Интерфейс описывает операции внешнего API:

```csharp
public interface IProductApi
{
    Task<ProductDto?> GetProductAsync(int id, CancellationToken ct);
    Task<IReadOnlyList<ProductDto>> SearchAsync(
        string query,
        CancellationToken ct);
}
```

Реализация получает настроенный `HttpClient` через конструктор:

```csharp
public sealed class ProductApi(HttpClient http) : IProductApi
{
    public async Task<ProductDto?> GetProductAsync(
        int id,
        CancellationToken ct)
    {
        using var response = await http.GetAsync($"products/{id}", ct);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<ProductDto>(ct);
    }
}
```

Клиент регистрируется в контейнере зависимостей:

```csharp
services.AddHttpClient<IProductApi, ProductApi>(client =>
{
    client.BaseAddress = new Uri("https://api.example.com/");
    client.Timeout = TimeSpan.FromSeconds(10);
    client.DefaultRequestHeaders.Accept.ParseAdd("application/json");
});
```

Благодаря этому адрес, заголовки и тайм-аут задаются в одном месте, а сервисы
зависят от интерфейса, а не от деталей HTTP-запроса.

### `DelegatingHandler`

`DelegatingHandler` — промежуточный обработчик исходящего запроса. Он подходит
для сквозного логирования, добавления заголовков, авторизации и сбора метрик.

Например, обработчик может добавить `X-Correlation-Id`, измерить длительность
запроса и записать результат в журнал. Correlation ID позволяет связать логи
нескольких сервисов, участвующих в обработке одной операции.

```csharp
services.AddTransient<CorrelationHandler>();

services.AddHttpClient<IProductApi, ProductApi>(client =>
{
    client.BaseAddress = new Uri("https://api.example.com/");
})
.AddHttpMessageHandler<CorrelationHandler>();
```

Сам обработчик должен вызвать `base.SendAsync`, иначе запрос не перейдёт к
следующему обработчику и не будет отправлен во внешний сервис.

## 3. Устойчивость HTTP-запросов

Внешний сервис может отвечать медленно, временно быть недоступным или возвращать
ошибки. Для таких ситуаций применяют timeout, retry и circuit breaker. В
современном .NET эти стратегии можно добавить через пакет
`Microsoft.Extensions.Http.Resilience`.

### Timeout

Timeout ограничивает время ожидания ответа. Он не даёт одному зависшему запросу
бесконечно удерживать ресурсы приложения.

Общий timeout ограничивает всю операцию, а timeout попытки — только один вызов.
Если используются retry, важно понимать, какой именно лимит задаёт каждая
стратегия и в каком порядке они включены.

Для отдельного вызова можно создать связанный `CancellationTokenSource`:

```csharp
using var timeoutCts = CancellationTokenSource
    .CreateLinkedTokenSource(cancellationToken);
timeoutCts.CancelAfter(TimeSpan.FromSeconds(2));

try
{
    return await productApi.GetProductAsync(id, timeoutCts.Token);
}
catch (OperationCanceledException)
    when (!cancellationToken.IsCancellationRequested)
{
    throw new TimeoutException($"Product API timeout for {id}");
}
```

Условие в `catch` отличает внутренний timeout от отмены запроса самим клиентом.

### Retry

Retry автоматически повторяет запрос после временной ошибки. Обычно повторяют
запросы при:

- сетевом исключении;
- ответе `408 Request Timeout`;
- ответе `429 Too Many Requests`;
- некоторых ответах `5xx`.

Между попытками используют экспоненциальную задержку: например, 0,5, 1 и 2
секунды. Jitter добавляет небольшой случайный разброс, чтобы множество клиентов
не повторили запрос одновременно.

Повторять все ошибки нельзя. Ответы `400`, `401`, `403` или `404` обычно не
исправятся от повторной отправки. Также опасно автоматически повторять операции,
которые изменяют данные, если они не являются идемпотентными.

### Circuit breaker

Circuit breaker временно прекращает запросы к нестабильному сервису. У него есть
три основных состояния:

1. **Closed** — запросы выполняются в обычном режиме.
2. **Open** — новые запросы сразу отклоняются без обращения к сервису.
3. **Half-open** — после паузы пропускается пробный запрос для проверки сервиса.

Например, circuit breaker может открыться, если за 30 секунд выполнилось не
менее 10 запросов и больше половины из них завершились ошибкой. После 15 секунд
он разрешит проверить, восстановился ли сервис.

Такой механизм уменьшает лишнюю нагрузку на уже неисправный сервис и позволяет
приложению быстрее сообщать об ошибке.

### Идемпотентность

Идемпотентная операция при повторном выполнении приводит к тому же результату,
что и при однократном. GET обычно идемпотентен, а POST, создающий заказ или
платёж, — нет: повторный запрос может создать дубликат.

Для безопасного повтора клиент передаёт уникальный ключ:

```http
Idempotency-Key: 3c7869a0-5c37-4a88-9fad-8266bd24cc77
```

Ключ необходимо создать один раз для логической операции и использовать во
всех её повторных попытках. Сервер сохраняет результат первой успешной
обработки и при повторном запросе с тем же ключом возвращает тот же результат,
не выполняя операцию заново.

Надёжная серверная реализация должна:

- хранить ключ вместе со статусом, телом и важными заголовками ответа;
- учитывать пользователя или клиента, которому принадлежит ключ;
- проверять, что с тем же ключом не пришло другое тело запроса;
- атомарно резервировать ключ до выполнения операции;
- корректно обрабатывать два одновременных запроса;
- задавать срок хранения ключей;
- использовать общее хранилище, например Redis или базу данных, если работает
  несколько экземпляров приложения.

Простая проверка кэша перед выполнением запроса недостаточна: два параллельных
запроса могут одновременно не найти ключ и оба создать ресурс.

## Итог

- Проекция и `AsNoTracking` делают read-only запросы EF Core экономнее.
- N+1 устраняется формированием результата на стороне базы данных.
- `Include` удобен для загрузки графа сущностей, а `AsSplitQuery` помогает
  избежать слишком большого JOIN.
- Сложные отчёты можно выполнять параметризованным SQL или через Dapper.
- `IHttpClientFactory` централизует конфигурацию клиентов и управление
  соединениями.
- `DelegatingHandler` добавляет общую обработку всех исходящих запросов.
- Timeout ограничивает ожидание, retry исправляет временные сбои, а circuit
  breaker изолирует нестабильный сервис.
- Retry изменяющих данные операций безопасен только вместе с корректно
  реализованной идемпотентностью.
