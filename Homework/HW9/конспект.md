# Аутентификация в ASP.NET Core: Cookie, JWT и BFF

## Аутентификация и авторизация

Аутентификация отвечает на вопрос «кто пользователь?», а авторизация — «что ему
разрешено?». После успешной аутентификации ASP.NET Core создаёт
`ClaimsPrincipal`. Он содержит идентификатор, имя, роли и другие claims.

Middleware подключаются до защищённых endpoint'ов:

```csharp
app.UseAuthentication();
app.UseAuthorization();
```

## Cookie authentication

Cookie подходит для браузерного MVC-приложения. После входа сервер создаёт
зашифрованный authentication ticket, а браузер автоматически отправляет Cookie
при следующих запросах.

Важные настройки:

- `HttpOnly` запрещает JavaScript читать Cookie;
- `Secure` разрешает передачу только по HTTPS;
- `SameSite` ограничивает межсайтовую отправку;
- `ExpireTimeSpan` задаёт срок сессии;
- `SlidingExpiration` продлевает активную сессию;
- `LoginPath` и `AccessDeniedPath` задают перенаправления.

Cookie автоматически прикладывается браузером, поэтому изменяющие запросы нужно
защищать antiforgery-токеном. `SameSite` полезен, но не заменяет полноценную
CSRF-защиту.

Claims создаются при входе, после чего вызывается `SignInAsync`. При выходе
используется `SignOutAsync`. Дополнительный `sid` позволяет хранить состояние
сессии на сервере и отзывать её до истечения Cookie.

## JWT Bearer

JWT обычно используется для API. Токен состоит из header, payload и подписи.
Payload не зашифрован, поэтому в него нельзя помещать пароли и секреты.

Сервер при проверке токена должен валидировать:

- подпись;
- issuer — кем выпущен токен;
- audience — для какого API он предназначен;
- срок действия;
- алгоритм подписи.

Access token делают короткоживущим. Клиент передаёт его явно:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

Стандартные claims: `sub` идентифицирует пользователя, `jti` — конкретный токен,
`iat` — время выпуска. Роли можно хранить в отдельных claims `role`.

## Refresh token и rotation

Refresh token нужен для получения нового access token без повторного ввода
пароля. Он должен генерироваться криптографически стойким генератором и иметь
достаточную энтропию.

При rotation использованный refresh token удаляется, а клиент получает новый.
Повторное применение старого значения отклоняется. В базе следует хранить хэш
refresh token, чтобы утечка хранилища не давала готовые токены злоумышленнику.

In-memory хранилище подходит только для демонстрации: после перезапуска данные
исчезают, а несколько экземпляров приложения не имеют общего состояния.

## Cookie и Bearer в одном приложении

Для разных частей приложения можно назначить разные политики:

```csharp
options.AddPolicy("Web", policy => policy
    .AddAuthenticationSchemes("Cookies")
    .RequireAuthenticatedUser());

options.AddPolicy("Api", policy => policy
    .AddAuthenticationSchemes("Bearer")
    .RequireAuthenticatedUser());
```

Policy scheme может автоматически выбрать обработчик: при наличии заголовка
`Authorization: Bearer` используется JWT, иначе Cookie. Явные политики всё равно
полезны, потому что не позволяют случайно открыть API через браузерную Cookie.

Ролевая авторизация добавляется через `RequireRole("admin")`. Для более сложных
правил применяют claims, requirements и собственные authorization handlers.

## BFF

Backend for Frontend располагается между браузером и внутренним API. Браузер
работает только с защищённой Cookie, а access и refresh tokens хранятся на
серверной стороне BFF. BFF прикладывает Bearer-токен к запросам во внутренний API.

Преимущество подхода: токены не доступны JavaScript и не хранятся в
`localStorage`. При этом BFF должен защищать изменяющие запросы от CSRF,
безопасно хранить серверные сессии и корректно обновлять токены.

## Практические правила

- Использовать HTTPS во всех недемонстрационных окружениях.
- Хранить ключи подписи и секреты вне репозитория.
- Не использовать простой SHA-256 для паролей; нужен `PasswordHasher`, bcrypt,
  scrypt или Argon2 с солью и подходящей стоимостью.
- Делать access token короткоживущим.
- Выполнять rotation refresh token и хранить его хэш.
- Защищать Cookie-запросы antiforgery-токенами.
- Разделять схемы и политики для HTML и API.
- Не записывать пароли, Cookie и токены в журналы.
